# Supabase account-recovery setup

The application code intentionally treats recovery as unavailable when required environment variables are absent. Configure these server variables in production:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` (server runtime only; never prefix with `NEXT_PUBLIC_`)
- `RECOVERY_HASH_SECRET` (at least 32 random characters; keep stable)
- `NEXT_PUBLIC_SITE_URL` (canonical HTTPS origin)
- `SUPABASE_PHONE_RECOVERY_ENABLED=true` only after phone authentication and an SMS provider are working

Apply `supabase/migrations/202608160001_account_recovery.sql` to an existing database. It is additive and idempotent and contains no `DROP`, `TRUNCATE`, `DELETE FROM`, or alteration of an existing application table. The service-role client is used only in server modules. Sensitive recovery tables have RLS enabled and no direct browser policies.

### Apply in Supabase Dashboard

1. Open the intended Supabase project and confirm the project name/reference in the top bar.
2. Make a database backup or confirm Point-in-Time Recovery before any production schema change.
3. Open **SQL Editor** and choose **New query**.
4. Open `supabase/migrations/202608160001_account_recovery.sql` locally, copy the entire file without modification, and paste it into the query.
5. Use the SQL Editor search to confirm there is no `DROP`, `TRUNCATE`, or `DELETE FROM` statement.
6. Select **Run** once. A successful execution returns without an SQL error; running the same complete file again is the idempotency check.
7. Open **Database → Tables** and confirm `account_recovery_requests`, `recovery_rate_limits`, `recovery_audit_log`, and `recovery_review_authorizations` exist with RLS enabled.
8. Open **Database → Functions** and confirm `record_recovery_attempt`, `submit_account_recovery_request`, and `review_account_recovery` exist.
9. In a separate SQL Editor query, grant the current platform owner review authority using their Auth user UUID (not an email): `insert into public.recovery_review_authorizations (user_id, authority) values ('OWNER_AUTH_USER_UUID', 'platform_owner') on conflict (user_id) do update set authority = excluded.authority;` Verify the UUID in **Authentication → Users** first.
10. Do not paste a service-role key into SQL Editor or browser code. Configure it only in the application server environment and redeploy.

## URL configuration

In **Authentication → URL Configuration**:

- Set Site URL to the canonical production HTTPS origin, for example `https://classes.example.com`.
- Add `https://classes.example.com/auth/callback` to Redirect URLs.
- Add each explicit preview/staging callback separately. Do not use a broad production wildcard.
- For local development add `http://localhost:3000/auth/callback` only to the development project.

For local testing, the exact URLs are:

- Site URL: `http://localhost:3000`
- Redirect URL: `http://localhost:3000/auth/callback`
- Password-recovery redirect generated by the app: `http://localhost:3000/auth/callback?next=/update-password`
- Post-exchange page: `http://localhost:3000/update-password`

The app passes `/auth/callback?next=/update-password` to `resetPasswordForEmail`. The callback allowlists the destination and exchanges the PKCE code before opening the password form.

## Email and SMTP

In **Authentication → Email Templates**, customize the password-recovery template but preserve Supabase's recovery link/token variables. Avoid wording that confirms whether an account exists. Test expired and reused links after every template change.

Configure a custom SMTP provider for production, verify its sending domain (SPF, DKIM and DMARC), choose a monitored From address, and keep provider credentials in Supabase rather than this repository. Review Supabase Auth email rate limits before launch.

## Phone recovery

Leave `SUPABASE_PHONE_RECOVERY_ENABLED` unset until **Authentication → Providers → Phone** is enabled and an SMS provider (such as Twilio, MessageBird or Vonage) is configured. Configure CAPTCHA and conservative Auth rate limits to control SMS abuse and cost. India deployments must also complete applicable TRAI/DLT registration. The UI sends OTP with `shouldCreateUser: false`; an invalid or expired code receives a generic error.

## Administrator MFA and recovery review

TOTP enrollment is available at `/account/security`. Admin sign-in is sent there until the session reaches AAL2. Only users explicitly listed in `recovery_review_authorizations` as `institution_owner` or `platform_owner` can execute `review_account_recovery`; every decision is written to `recovery_audit_log`. Approval records a decision—it never sets or transmits a password. Contact changes must use Supabase verification flows.

The additive migration deliberately does not alter `profiles`. Grant review authority by inserting the existing owner's user ID into `recovery_review_authorizations` with `authority = 'platform_owner'` using the SQL Editor or another service-role-only administrative process. Ordinary administrators receive no row and cannot approve recovery.

Keep Supabase MFA verification enabled. For stronger enforcement, add restrictive RLS policies requiring the JWT `aal` claim to be `aal2` on administrator-only tables after all current administrators have enrolled, so rollout does not strand existing owners.

## Operational checks

Before production, verify recovery emails, invalid/expired/reused links, invalid SMS codes, rate limits, owner-role restrictions, audit retention, and session invalidation. The password update signs out other sessions where supported by Supabase. Never log form bodies, OTPs, recovery links, service-role keys or authenticator secrets.
