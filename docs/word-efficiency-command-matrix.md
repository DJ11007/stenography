# Word Efficiency command matrix

Audit date: 2026-08-25 (revised same day after two repair passes). This matrix originally described the implementation before any functional repair; rows marked `Functional` below reflect fixes landed since. `Covered` means a PostgreSQL or executable unit test exercises behavior; `Contract only` means tests inspect source text; `None` means no meaningful runtime coverage.

**Repair pass 1** (correctness/serialization): list/bullet/numbering structural round-trip, drop cap and line-number restoration, watermark autosave, `find` real jump-to-match, cursor-relative table row/column edits, `fullScreenReading` now genuinely read-only, per-side margins, a real thumbnails panel, measured zoom fit, and a critical unrelated regression where a student's DB autosave was never restored on page reload.
**Repair pass 2**: `window.prompt`-based commands (margins, watermark, page color, columns, page size, symbol, table insert/edit) replaced with in-app dialogs; and — the larger fix — **automatic rule-based grading is now actually wired up**. Admins could already author explicit grading rules per question, but nothing evaluated them; `submit_word_efficiency_document` now evaluates authored rules against the final document at submission time and pre-populates scores (admin can still review/override before publishing). See [supabase/migrations/202608250017_word_efficiency_automatic_grading.sql](../supabase/migrations/202608250017_word_efficiency_automatic_grading.sql).
**Repair pass 3**: `zoom` previously had no ribbon handler at all (clicking it silently did nothing, despite `zoom100`/`onePage`/`twoPages`/`pageWidth` all working) — it now opens a real percentage dialog (200/150/100/75/50% presets plus a custom 10–500% field) and is correctly excluded from the operations audit trail as a view-only setting. `sort` previously always reordered the *entire* document regardless of selection and offered no ascending/descending choice; it now opens a Sort dialog and, when more than one paragraph is actually selected, reorders only those paragraphs back into their own positions — untouched paragraphs never move.

## Cross-cutting implementation status

- The persisted JSON model is bounded, but many DOM insertion commands do not round-trip into their declared block/run types.
- Legacy `document.execCommand` remains only for commands still marked Partial; exact point sizing, multi-paragraph paragraph scope, formatting painter, case conversion, clearing, indentation, replacement, and Select All now use explicit Range/block operations.
- View-only and selection-only commands are excluded from saved operation history and do not schedule autosave.
- Database capability comparison covers structured features, timing, ownership, autosave, normal submission, and grace submission. Migration 013 must remain additive and must not rewrite stored history.
- Grading retains secure teacher fallback and immutable publication. Explicit rules are authored independently of question prose with exact target, expected operation/value, allocated marks, and optional partial marks. Migration 014 stores one immutable rule per version/question and locks it after attempt preparation. `evaluateWordGradingRule` compares immutable original/final snapshots and reports unrelated leaf changes; focused tests cover exact, partial, unrelated-change, and no-free-text-inference behavior. **As of migration 017, authored rules are actually evaluated**: `submit_word_efficiency_document` runs a PL/pgSQL port of the same target-resolution/match logic once, at submission, and pre-populates `word_efficiency_question_scores.awarded_marks` for any question with a rule (`graded_by` stays null as the "system-graded, not yet reviewed" signal). Questions without a rule are untouched and stay fully manual. The admin grading form flags pre-filled rows for review before publishing.
- Student results show “Submitted — evaluation pending” before publication and question-wise marks only after publication; draft grading and private notes remain hidden.
